模型方块打开卡顿 — 性能分析与优化表

项目：BBS-Cubed（mchorse/bbs_mod） · 分析日期：2026-09-11 · 现象：右键打开模型方块编辑界面时卡顿数秒

① 打开模型方块时发生了什么

右键模型方块后，客户端会依次执行以下步骤（按耗时热度标注）：

  • 服务器回包，客户端收到"打开面板"消息 — 几乎无开销
  • BBSModClient.getDashboard() → 首次调用时 new UIDashboard() 一次性构建全部 8 个面板 — 最大嫌疑（一次性）
  • 若该方块的模型尚未加载，加载完成后 VAO 烘焙被排入主线程执行 — 大模型可达数秒
  • UIScreen.open() → 面板 open() → 刷新方块列表、填充数据 — 较轻
  • 面板每帧渲染：Gizmo 拾取模板缓冲（全屏 Framebuffer + 像素读取） — 持续 FPS 损耗，非开卡顿

② 优化表（按优先级排序）

优先级问题点发生时机原因分析建议优化预计收益
P0 Dashboard 全量构建
BBSModClient.getDashboard()
UIDashboard.registerPanels()		 进存档后第一次打开 BBS 界面（含点模型方块） 一次构造 8 个面板：UIFilmPanel（剪辑面板+回放编辑器+撤销系统+Dock 布局的巨型 UI 树）、变形、模型编辑器、纹理管理、音频编辑、图表、全部设置项、涂鸦板，全部在渲染线程同步完成 改为懒加载：只构建当前使用的面板，切换到哪个面板再建哪个；或在进入世界后于后台空闲时机预热构建 首次打开卡顿从数秒降至接近 0；收益最大
P1 VAO 烘焙占用主线程
ModelInstance.setup() →
CubicVAOBuilderRenderer		 模型首次加载完成后（如刚放置/重载/换模型后打开方块） 模型文件解析已在后台线程（✔ 这点没问题），但烘焙阶段遍历全部 Cube/Mesh、构建顶点数组、计算切线、上传 GPU，被 MinecraftClient.execute() 排到主线程一次性执行 把 VAO 烘焙分帧/分批执行（每帧只烘焙若干 Group），或移到后台构建数据、仅 GL 上传留在主线程 大模型从"卡几秒"变"渐进出现"，彻底消除尖峰
P2 表单编辑器重复创建
UIModelBlockPanel.pickEdit 回调		 每次点击面板上的"编辑 / 选择"按钮 每次点击都 new UIFormPalette()，整套表单编辑 UI 重新构建 缓存并复用 UIFormPalette 实例，仅在 form 变化时刷新内容 点击"编辑"不再卡顿
P3 Gizmo 拾取每帧开销
renderGizmoStencilInterface()		 面板打开期间的每一帧 每帧绑定全屏模板 Framebuffer 重画把手、再回读像素判断悬停，还有悬停高亮全屏贴回 仅在鼠标移动/按下时执行拾取；静态帧直接复用上次结果 提升打开界面期间的 FPS（低配机明显）
P4 模型方块渲染距离过大
ModelBlockEntityRenderer.getRenderDistance() = 512		 世界中模型方块较多时，持续开销 512 格内的所有模型方块都参与渲染与 look-at 计算 提供可配置渲染距离（默认 128~256）；或按包围盒做视锥剔除 方块多的地图 FPS 更稳
P5 "全局渲染"开关重建整个世界
worldRenderer.reload()		 在模型方块面板切换 Global 开关时 为刷新渲染缓存而重建全部区块，属于"杀鸡用牛刀" 只让相关 BlockEntity 重新入列/剔除，避免整世界 reload 消除切换开关时的秒级卡顿

③ 结论

排查确认：模型文件解析本身已在后台线程（ModelLoader "BBS model loader" 线程），不是卡顿元凶。 卡顿来自两条主线程路径：① 首次打开时 Dashboard 及其 8 个面板的全量构建（P0）；② 模型加载完成后排入主线程的 VAO 烘焙（P1）。 用户"每次打开都卡"的体感，多数情况是 P0（每次进存档后的第一次）与 P1（模型刚被加载/重载）叠加造成。

本报告仅分析、未做任何代码改动。若确认执行优化，建议按 P0 → P1 → P2 顺序逐项实施，每项单独提交便于回归验证。

④ 上线优化前如何验证（可选）

  1. 安装 Spark 性能分析器，执行 /spark profiler start → 打开模型方块 → /spark profiler stop，查看主线程热点是否落在 UIDashboard.<init> 与 CubicVAOBuilderRenderer，即可实锤 P0/P1。
  2. 同存档测两次：进存档后第一次打开 vs 第二次打开。若第一次明显更卡 → P0 为主；若两次都卡且模型较大 → P1 为主。
  3. 对照测试：把模型的 config 中 onCpu 设为 true（跳过 VAO 烘焙）再打开，若不卡则确认 P1。
