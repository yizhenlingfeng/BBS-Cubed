## 0. 一句话结论

**1.21.11 现在「能编译、能进游戏、能玩」，但所有渲染增强全线下线。** 82 个源文件（13,785 行）被 `build.gradle` 排除，产物比 1.20.1 少 102 个 class。缺的不是「几个特效」，而是三条链路：

| 缺的链路 | 后果 | 归属 |
| --- | --- | --- |
| **模型着色管线**（tint / whiten / glint / 逐骨骼 PBR / 动态 UV / 纹理覆盖） | 模型、拖尾、广告牌、挤出体、流体全部退化为原版外观 | WP2 |
| **屏幕后处理 + HUD 剪辑**（调色 / 暗角 / 畸变 / VHS / 色差 / 径向模糊 / 快捷栏剪辑） | 电影模式的颜色氛围全没了 | WP3 |
| **粒子与第三方**（AAA Particles、Particle Plus、VFX 破坏魔杖、IRLite 物品阴影） | 每帧可见的创作素材缺失 | WP4 / WP5 |

外加 **编辑器 UI 的一半功能面板**（WP6）、**世界播放 / 光影曲线 / Iris**（WP7）、**发光方块**（WP8）。

关键判断：**WP1（着色地基）是关键路径**。1.21.11 不允许「给 RenderLayer 挂自定义 uniform」——`RenderLayer` 只绑引擎内建 uniform，自定义参数必须在 `RenderPass` 里逐 pass `setUniform`。所以 WP2 / WP4 都不能在旧注入点上「补两行」，必须先写一层 `RenderPipeline + std140 UBO + 手写 pass` 的地基（**WP3 例外**：1.21.11 自带 `PostEffectPipeline` + `PostEffectProcessor` 的屏幕后处理框架，可以独立推进，见 WP3 节）。这一层大约 400–600 行新代码，但决定了后面 12k 行能不能按原逻辑照搬。

## 2. 地基：1.21.11 渲染契约

这一节是整个计划的依据。先看清楚新管线长什么样，再谈怎么改。

### 2.1 四种落点，各有边界

| 落点 | 能做什么 | 不能做什么 | 在 BBS 1.21.11 里的例子 |
| --- | --- | --- | --- |
| **`RenderLayer` + `layer.draw(BuiltBuffer)`** | 用预建 pipeline 画一批同层几何；引擎自动绑 `DynamicTransforms` / `Projection` / `Fog` / `Lighting` | **不能带自定义 uniform**，只能绑 layer 声明时命名的纹理 | `BBSShaders.getModelLayer` / `getBoundModelLayer` |
| **`RenderPipeline` + 手写 `RenderPass`** | 完整控制：自定义 std140 UBO、多纹理、blend/depth 状态、渲染目标 | 要自己管编码器、uniform 写缓冲、顶点缓冲上传 | `ScreenQuadPass.draw`、`BBSPickerRenderer.draw` |
| **`Batcher2D` + `ImmediateGui`** | 2D/HUD 叠加，自动处理 GUI 变换与批处理 | 不适合 3D 世界几何 | `BBSRendering.onWorldRenderEnd` 里的 `FrameOverlays.render` |
| **原生后处理 `PostEffectPipeline` + `PostEffectProcessor`** | 全屏 pass 链、ping-pong target、参数化 uniform block，target 与 pass 状态由引擎管理 | 只能做屏幕空间效果：拿不到模型/几何，也插不进半透明队列 | `InterfaceBlur`（双 Kawase，5 级 ping-pong） |

**结论**：模型着色（WP2）必须走第二种——tint/whiten/glint 都是**逐 draw 变化的片元参数**，而 `RenderLayer` 无法携带它们；屏幕后处理（WP3）走第四种（原生框架，多 pass 免费）；HUD（A9）走第三种。

### 2.2 模型绘制的现状链路

```
CubicRenderer / BOBJ
   ↓ 写顶点（POSITION_COLOR_TEXTURE_OVERLAY_LIGHT_NORMAL）
ModelInstance.java:667 ──┐
BOBJModelVAO.java:386 ───┤
ModelVAORenderer.java:60 ┤→ FormTranslucentQueue.submit(built, ModelVariant, Texture, alpha, StencilMap, origin, tinted)
BillboardFormRenderer:346┤        ↓ 按 camera 距离排序
TrailFormRenderer:366 ───┘        ↓ bufferCommands / groupCommands
                                  ↓ FormTranslucentQueue.add(DrawCommand) → command.draw() → layer.draw(built)
```

五个 `submit` 调用点是**全部**的世界路径收口（另有 `FramebufferFormRenderer:489/521` 用 `isActive()+add(BufferCommand)`、`LabelFormRenderer:178/184` 用 `beginGroup`）。预览路径（编辑器里）绕开队列，直接 `layer.draw(built)`（`ModelInstance:658`、`BOBJModelVAO:380`）。

这个结构对我们是**好消息**：几何已经是「每次 draw CPU 重发 `BuiltBuffer`」，没有 VBO 常驻需要同步；`FormTranslucentQueue.DrawCommand` 是 `public static abstract class`，构造函数 `protected DrawCommand(Vector3f cameraSpaceOrigin)`、抽象方法 `public abstract void draw()`，且 `add(DrawCommand)` 是 public。也就是说——

> **我们可以写一个自定义 `DrawCommand`，在 `draw()` 里开自己的 `RenderPass` 并设自定义 UBO，同时继续参与队列的远近排序，不必绕开队列。**

这直接解决了「自绘 pass 会破坏半透明排序」的问题（ADR-2）。

### 2.3 旧注入点的存亡对照

| 1.20.x 用的东西 | 1.21.11 现状 | 替代 |
| --- | --- | --- |
| `new ShaderProgram(factory, name, format)` | 无此类 | `RenderPipeline.builder()` + `RenderPass.setPipeline` |
| `GlUniform.set(...)` / `GlUniform.uploadAll()` | `GlUniform` 已是接口，不能直接写 | `pass.setUniform(name, GpuBufferSlice)`（std140 UBO）或 `RenderSystem.bindDefaultUniforms(pass)` |
| `AbstractTexture.addSampler("Sampler0", tex, sampler)` | 只能由 layer 声明时绑定 | `pass.bindTexture("Sampler0", view, sampler)` |
| `RenderSystem.enableBlend()` / `depthFunc` / `disableCull` | 全局状态调用被移除 | `RenderPipeline.builder().withBlend(...)` / depth 配置 / `ModelVariant.cull` |
| `BufferRenderer.drawWithGlobalProgram(built)` | 无 | `pass.setVertexBuffer` + `RenderSystem.getSequentialBuffer` + `pass.drawIndexed`（见 `ScreenQuadPass.draw`） |
| `BBSShaders.getProgram(...)` / `getShader(...)` / `setupUniforms(...)` | **全部不存在** | 无直译，见 §2.5 |
| `FormRenderer.getShader(...)`（A2/A3 旧的注入点） | 无此方法；材质解析被外移成 `ModelInstance.render` 的回调 | `ModelInstance.render(..., Function<String, Texture> textureResolver)`（`ModelInstance.java:550`）——**包一层 resolver 就能替换每个 material 的纹理，不必 mixin 私有方法**；调用侧是 `ModelFormRenderer.renderModel`（457）/`albedo`（1004）/`materialLink`（975） |
| `Particle.red/green/blue/alpha`（`ParticleColorAccessor`） | 字段搬到 `BillboardParticle`（`protected float red/green/blue/alpha`，`public setColor(float,float,float)`，`protected setAlpha(float)`） | 把 `@Mixin` 目标从 `Particle` 改成 `BillboardParticle`，几乎零成本 |

### 2.5 三条硬结论

1. **没有 `getProgram`/`setupUniforms` 可以复用了。** 模型侧的自定义着色只有一条路：**自己的 pipeline + 自己的 pass + 自己的 UBO**（`ScreenQuadPass` / `BBSPickerRenderer` 是范本）。屏幕后处理是**例外**：1.21.11 有原生 `PostEffectProcessor` 框架（见上），能把整条 pass 链连同 target 管理交给引擎；不要拿手写 pass 去做全屏链，也不要指望原生框架给你逐 draw 的模型参数。
2. **逐 draw 参数用 std140 UBO，不要用 per-draw uniform 循环。** `MappableRingBuffer` + `writeUbo(...)` 已经是 BBS 的既有约定，复用它能蹭到引擎的 frame-in-flight 管理。
3. **不要绕开 `FormTranslucentQueue`。** 半透明排序、`StencilMap` 拆分、Iris 世界表单的特殊处理都在队列里（`isActive()` 还要判 `BBSRendering.isIrisShadowPass()`）。用自定义 `DrawCommand` 入队，既保留排序又保住自定义 pass。

**做法要点**

**`GradePipeline` 的建法（第十二轮实测，照上游 `BBSShaders.modelPipeline` 逐行抄）**

```java
Identifier shader = Identifier.of("bbsplusplus", "core/model_texture_grade");

RenderPipeline.Builder builder = RenderPipeline.builder()
    .withLocation(Identifier.of("bbsplusplus", "pipeline/model_grade" + variant.suffix() + (world ? "_world" : "")))
    .withVertexShader(shader)
    .withFragmentShader(shader)
    .withVertexFormat(VertexFormats.POSITION_COLOR_TEXTURE_OVERLAY_LIGHT_NORMAL, VertexFormat.DrawMode.QUADS)
    .withBlend(BLEND)                                            /* 与 BBSShaders.BLEND 同一个 BlendFunction */
    .withDepthTestFunction(DepthTestFunction.LEQUAL_DEPTH_TEST)
    .withDepthWrite(variant.depthWrite())
    .withCull(variant.cull())
    /* 四内建 block 的顺序不能改：上游注释写明按 DynamicTransforms → Projection → Fog → Lighting
     * 声明，引擎才会绑；少一个模型 shader 链不上，世界绘制全变 no-op。 */
    .withUniform("DynamicTransforms", UniformType.UNIFORM_BUFFER)
    .withUniform("Projection", UniformType.UNIFORM_BUFFER)
    .withUniform("Fog", UniformType.UNIFORM_BUFFER)
    .withUniform("Lighting", UniformType.UNIFORM_BUFFER)
    .withUniform("GradeParams", UniformType.UNIFORM_BUFFER)      /* 我们自己的 std140 block */
    .withSampler("Sampler0")                                     /* 原图 */
    .withSampler("Sampler1")                                     /* overlay swatch */
    .withSampler("Sampler2");                                    /* 光照图 / glint */

if (variant.pass() != FormTranslucentQueue.PASS_SINGLE)
{
    builder.withShaderDefine("PASS_MODE", variant.pass());
}

RenderPipeline pipeline = RenderPipelines.register(builder.build());   /* public，AW 不用放宽 */

if (world)
{
    /* 光影镜像：否则 Iris 下我们的 pipeline 不被当成实体管线，模型直接不画，还会丢阴影。 */
    BBSRendering.mirrorIrisPipeline(pipeline, modelPrototype(variant));
}
```

- `RenderPipeline.Builder` 的方法已逐个 `javap` 核实：`withLocation` / `withVertexShader` / `withFragmentShader` / `withVertexFormat(VertexFormat, DrawMode)` / `withBlend(BlendFunction)` / `withDepthTestFunction(DepthTestFunction)` / `withDepthWrite(boolean)` / `withCull(boolean)` / `withUniform(String, UniformType)` / `withSampler(String)` / `withShaderDefine(String, int)` / `build()`。
- `RenderPipeline.builder(Snippet...)` 可以完全不带 snippet（上游模型管线就是空的），所以 **AW 里那条 `POSITION_COLOR_SNIPPET` 只对描边那三个自定义 pipeline 有用，GradePipeline 不需要它**。
- `modelPrototype(variant)` 照抄上游（`libs/bbs-fs-1.21.11/src/client/java/mchorse/bbs_mod/client/BBSShaders.java:678`）：`PASS_TRANSLUCENT` → `RenderPipelines.ENTITY_TRANSLUCENT`；否则 `variant.cull() ? RenderPipelines.ENTITY_CUTOUT : RenderPipelines.ENTITY_CUTOUT_NO_CULL`。
- 我们的 shader 骨架直接抄 `libs/bbs-fs-1.21.11/src/main/resources/assets/bbs/shaders/core/model.vsh`（945 B，最小可用：`Position` / `Color` / `UV0` / `UV1` / `UV2` / `Normal` + `minecraft_mix_light` + `minecraft_sample_lightmap`），把 1.20 `model_texture_grade.fsh` 的 HSL/whiten/glint 数学补进 fsh，uniform 改成 `layout(std140) uniform GradeParams { vec4 Tint; vec4 GlintColor; float Whiten; float GlintStrength; float GlintPhase; float GlintBrightness; };`。

**`GradeUniforms` / `GradeDrawCommand` 的两个硬约束**

- UBO 必须在**开 pass 之前**写完：`MappableRingBuffer.rotate()` 有 fence，pass 开着时写会失败（`ScreenQuadPass.writeUbo` 的 javadoc 原话）。
- 模型必须给**深度附件**：`encoder.createRenderPass(Supplier<String>, GpuTextureView color, OptionalInt clearColor, GpuTextureView depth, OptionalDouble clearDepth)` 这个带深度的 5 参重载才可用；`Framebuffer.getColorAttachmentView()` / `getDepthAttachmentView()` 都是 public，直接用主 framebuffer。

**验收**：`build12111` 绿；控制台无 `Missing uniform block` / `Unknown uniform` 警告；把 `GradePipeline` 临时挂到 `OutlineRenderer121` 的模型绘制点能画出与原版一致的模型（颜色/光照不偏）；开 Iris 后模型不消失、阴影仍在；关 Iris 时 `FormTranslucentQueue` 的远近排序与 1.20 一致。

**预估**：`GradePipeline` 0.5 人日、`GradeUniforms` 0.5、`GradeDrawCommand` 0.5、`GradeCtx` 0.5、两个 UBO/深度变体的试错 0.5–1 —— 合计 2–3 人日，落在关键路径上。

### WP2 — 模型着色扩展（3.5–5 人日，依赖 WP1；A1/A3/A4 已有参考实现）

**目标**：A1（附魔光效）、A2（逐骨骼 PBR）、A3（纹理调色/白化）、A4（动态 UV）、A5（骨骼纹理覆盖）、A6（逐肢体剔除）。

**涉及文件（17 个 / 1,911 行）**：`client/screen/ModelTextureGradeShader.java`（367）、`client/screen/TextureGradeRenderContext.java`（95）、`mixin/client/ModelInstanceTextureGradeMixin.java`（149）、`mixin/client/ModelVAOMixin.java`（54）、`mixin/ModelVAORendererMixin.java`（91）、`mixin/ModelInstanceMixin.java`（约 170）、`mixin/BOBJModelVAOMixin.java`（62）、`mixin/TrailFormRendererMixin.java`、`mixin/BillboardFormRendererMixin.java`、`mixin/ExtrudedFormRendererMixin.java`、`mixin/ModelFormRendererEquipmentMixin.java`、`mixin/CubicCubeRendererUvEmitMixin.java` 等（完整 17 条见附录 A）。

**做法要点**

**逐骨参数怎么进 shader（第十一轮核实：1.21.11 的投递契约）**

- **1.21.11 的模型绘制粒度是「每 material 一次 draw」，不是每骨**：`ModelInstance.render`（`libs/bbs-fs-1.21.11/src/client/java/mchorse/bbs_mod/cubic/ModelInstance.java:550`）里 `renderPasses(textureResolver)`（`:528`）返回 `[""] + materials`，每个 pass 各开一个 `Tessellator.begin(QUADS, POSITION_COLOR_TEXTURE_OVERLAY_LIGHT_NORMAL)` → `CubicRenderer.processRenderModel(...)` → `endNullable()` → `FormTranslucentQueue.submit(...)`（`:667`）。**同一个 pass 内所有骨骼共享同一份 uniform**——所以 1.20 那种「在 `CubicVAORenderer` 里逐组 `GlUniform.set`」的路在 1.21.11 不存在（`CubicVAORenderer` 类已被删）。
- **逐骨 tint 上游已经原生实现，不需要我们做**：`FormOverlay.beginPalette()` + `renderProcessor.setOverlayPalette((group) -> FormOverlay.slot(FormOverlay.combine(modelForm, tintMaterial, group)))`（`:609-611`），颜色写进 swatch 纹理的 texel，顶点用 UV1 指过去。前提是 `tintable`：`stencilMap == null && overlay == OverlayTexture.DEFAULT_UV && this.form instanceof ModelForm`（`:554`）。→ **A3 的「逐骨叠加色」这一半白送**，我们只需补 form 级的 HSL tint 与 whiten。
- **逐 material 纹理也原生**：`textureResolver.apply(material)` → `BBSModClient.getTextures().bindTexture(...)`，draw 取 `getLastBound()`（`:585-589`、`:669`）；BOBJ 按 mesh 名解析（`:700`）。PBR 变体（`FormPbr.resolveAlbedo`）本来就走 `ModelFormRenderer.albedo(material, link)`（`:1004`），也是 per-material。→ **A2/A5 的「换纹理」部分只需包一层 resolver，零 mixin**。
- 于是「逐骨」只剩三条投递通道，按成本排序：
  1. **overlay swatch（已有，零成本）**：装得下颜色类逐骨参数（RGB + 一个 alpha 标量）。
  2. **逐骨拆 draw（推荐）**：复制一份 `CubicRenderer.processRenderModel` 的 70 行 walk（它只是 `renderGroup` + 递归；`ICubicRenderer.renderGroup(BufferBuilder, MatrixStack, ModelGroup, Model)` 就是逐骨钩子，见 `libs/bbs-fs-1.21.11/src/client/java/mchorse/bbs_mod/cubic/render/ICubicRenderer.java:94`）。遇到「该骨参数非中性」时 `builder.endNullable()`，把这段几何包成自建 `FormTranslucentQueue.DrawCommand`（构造时记 `distanceSq` 参与远近排序），然后接着走下一骨；中性骨（绝大多数）仍并进全模型那一次 draw。**代价只在有非默认值的骨上多几次 draw。**
  3. **参数贴图 + 逐顶点骨索引（不推荐）**：要给 `CubicCubeRenderer` 的顶点写入加一列（现在写死 `POSITION_COLOR_TEXTURE_OVERLAY_LIGHT_NORMAL` 七元素），改动面比通道 2 大、收益一样。
- **通道 2 的 DrawCommand 完整配方（每一步都在 `ScreenQuadPass` / `FormTranslucentQueue` 里验证过）**：

```java
public final class ModelGradeCommand extends FormTranslucentQueue.DrawCommand
{
    /* 父类只有 protected DrawCommand(Vector3f cameraSpaceOrigin)，distanceSq 由它算好 */

    @Override
    public void draw()
    {
        /* UBO 必须在开 pass 之前写完（MappableRingBuffer 的 rotate 有 fence） */
        GpuBufferSlice params = GradeUbo.write(buf -> buf.putVec4(tintR, tintG, tintB, whiten)
            .putFloat(glintStrength).putFloat(glintBrightness).putVec4(glintColor));

        CommandEncoder encoder = RenderSystem.getDevice().createCommandEncoder();
        Framebuffer fb = MinecraftClient.getInstance().getFramebuffer();

        try (RenderPass pass = encoder.createRenderPass(() -> "bbspp:model_grade",
                fb.getColorAttachmentView(), OptionalInt.empty(),
                fb.getDepthAttachmentView(), OptionalDouble.empty()))
        {
            pass.setPipeline(GradePipelines.model(variant));
            RenderSystem.bindDefaultUniforms(pass);          /* DynamicTransforms / Projection / Fog / Lighting */
            pass.setUniform("GradeParams", params);          /* 我们自己的 std140 block */

            AbstractTexture albedo = MinecraftClient.getInstance().getTextureManager().getTexture(albedoId);
            pass.bindTexture("Sampler0", albedo.getGlTextureView(), albedo.getSampler());

            pass.setVertexBuffer(0, vertexBuffer);
            pass.setIndexBuffer(indexBuffer, indexType);
            pass.drawIndexed(0, 0, indexCount, 1);
        }
    }
}
```

- 上面用到的实测事实：**带深度**的 `createRenderPass` 重载存在（模型必须给 depth，否则遮挡错乱；`ScreenQuadPass` 用的是无深度的 3 参重载，不能照抄）；`Framebuffer.getColorAttachmentView()` / `getDepthAttachmentView()` 都是 public；`AbstractTexture.getGlTextureView()` / `getSampler()` 是 public（BBS 的原始 GL 纹理经 `AdoptedTexture.identifier(Texture)` 注册成 vanilla 纹理后就能取到 view，见 `libs/bbs-fs-1.21.11/src/client/java/mchorse/bbs_mod/graphics/texture/AdoptedTexture.java:62`）；`RenderPass` 有 `setUniform(String, GpuBufferSlice)` 与 `bindTexture(String, GpuTextureView, GpuSampler)`。
- **参数从 bone 走到命令的接线点**：逐骨参数都挂在 `ModelGroup` 上（`GroupPbrHolder` / `BonePbrHolder` / `GroupGlintHolder` / `GroupTextureHolder` / `enableCull` 那一批 holder），walk 时按当前 `group` 取值、写进下一条命令的参数字段。**这些 holder 的注入点不碰旧渲染 API，可以从被排除的 mixin 里原样留用**，这也是 WP2 里唯一「改 mixin 不改逻辑」的部分。
- 与 WP1 的关系：通道 2 需要 WP1 的 `GradePipelines`（pipeline + `GradeParams` UBO 声明 + 4 个 define 变体）；通道 1 不需要 WP1。**建议先做通道 1 把 A3 的逐骨叠加色调通，再上通道 2 做 A1/A2/A5。**

**被排除的那批模型 mixin 怎么办（§2.6 的结论）**

- `mixin/ModelInstanceMixin`：`drawImmediate` 已死，`render` / `renderHybrid` / `isVAORendered` 仍在 → 只删失效的注入。
- `mixin/ModelVAORendererMixin`：`setupUniforms` 已死（1.21.11 的 `ModelVAORenderer` 里没有这个方法），`render` 在 → 改成在 `render` 入口塞 `GradeCtx`，uniform 走 UBO。
- `mixin/ModelVAOMixin`：`upload` 已死（`ModelVAO` 现在只有 `writeImmediate`）→ 该 mixin 可整个删掉，几何本来就每帧 CPU 重发。
- `mixin/client/ModelInstanceTextureGradeMixin`：抓 `Supplier<ShaderProgram>` 的注入点已不存在 → 整段重写为「包 resolver + 包 `render` 调用」，或直接删掉、改由 `GradeCtx` 从调用侧驱动。
- `mixin/ExtrudedFormRendererMixin` / `CubicVAORendererMixin` / `CubicVAORendererLimbCullingMixin`：`CubicVAORenderer` 与 `IModelVAO` 两个类被删（§2.7 里唯二「类级死亡」）→ 前者删，后两者的「逐肢体剔除」语义迁到 `ModelVariant.cull` 与 `FormTranslucentQueue.submit` 的 `cull` 参数上（`ModelVAORenderer.render(..., boolean cull)` 已把它带进 `ModelVariant`）。
- `mixin/BOBJModelVAOMixin`（目标 `render/unbind` 都在）、`BillboardFormRendererMixin`、`TrailFormRendererMixin`、`CubicCubeRendererUvEmitMixin`（目标类在）：保留注入点，把里面 `GlUniform`/`RenderSystem.setShader` 的调用换成 `GradeCtx` 记录。

**第十六轮 spike（实测错误画像，2026-11-03）**：把 17 个文件全部解除排除后 `build12111`，**73 个编译错误、集中在 11 个文件，另有 6 个文件零错误**（`TextureGradeRenderContext`、`ModelVAOMixin`、`FormRendererTextureGradeContextMixin`、`BBSShadersTextureGradeMixin`、`BOBJModelVAOMixin` 及另一条纯数据类）。错误量前四：`ModelTextureGradeShader` 19、`ExtrudedFormRendererMixin` 15、`ModelInstanceMixin` 13、`CubicVAORendererMixin` 5 —— 也就是说 47/73 集中在 3 个文件，**WP2 的工程量几乎就是这 3 个文件的重写**。

### WP3 — 屏幕后处理与 HUD（3–4 人日，**不依赖 WP1**）

**目标**：A8（颜色/电影剪辑屏幕效果：调色、暗角、畸变、VHS、色差、径向模糊）、A9（快捷栏剪辑 HUD）。

**做法要点**

- **首选：走原版 `PostEffectPipeline` + `PostEffectProcessor`**，这条路在 1.21.11 上已被上游验证可用：`libs/bbs-fs-1.21.11/src/client/java/mchorse/bbs_mod/ui/utils/InterfaceBlur.java`（296 行）用它跑通了 5 级双 Kawase ping-pong。契约（`javap` 核实）：
  - `PostEffectPipeline` 是 record：`(Map<Identifier, Targets>, List<Pass>)`；`Targets(Optional<Integer> width, Optional<Integer> height, boolean persistent, int clearColor)`；`Pass(Identifier vertexShaderId, Identifier fragmentShaderId, List<Input> inputs, Identifier outputTarget, Map<String, List<UniformValue>> uniforms)`；`TargetSampler(String samplerName, Identifier targetId, boolean useDepthBuffer, boolean bilinear) implements Input`。
  - `UniformValue` 的实现：`FloatValue` / `IntValue` / `Vec2fValue` / `Vec3fValue` / `Vec3iValue` / `Vec4fValue` / `Matrix4fValue`。
  - `ProjectionMatrix2(String name, float near, float far, boolean ortho)` 在 `net.minecraft.client.render.ProjectionMatrix2`（**不是** `client.gl`）。

- **Iris / `isCustomSize` 下要单独验**：R3 已登记「原生后处理链在 `isCustomSize` / Iris 下黑屏」的风险，`InterfaceBlur` 自己也是 `broken` 降级 —— 我们的效果要加同样的 try/catch 与「失败即关闭效果」的开关。

**验收**：调色/暗角/畸变/VHS/色差/径向模糊六种效果逐个可见，参数滑块变化实时反映；`isCustomSize` 与 Iris 开关四种组合下不黑屏、不闪；快捷栏剪辑在 HUD 上位置正确、不遮挡调试屏；关闭效果时零额外开销（不建 pipeline）。

**预估**：`PostEffectPipeline` 包装 + 首个效果打通 1–1.5 人日；六种效果数学搬运 1–1.5；HUD 0.5；Iris/`isCustomSize` 加固 0.5–1 —— 合计 3–4 人日，可与 WP1 并行。

### 4.3 与旧清单顺序的差异及理由

旧清单 §4 的顺序是：守卫 → P0 屏幕后处理 → P0 模型 shader → P1 粒子 → P1 纯 UI → P2 mixin 小功能 → P2 方块 → P2 世界播放。

**改了两处**：

1. **把「模型 shader」提到主线上，并拆出 WP1 地基；屏幕后处理降为可并行的独立分支。** 旧顺序里屏幕后处理先做，理由是「效果最显眼」；但源码核对后发现屏幕后处理**不需要**手写 pass 那套地基——1.21.11 的原生 `PostEffectPipeline` 已经够用（`InterfaceBlur` 是现成范本，见 WP3）。真正吃掉地基的是模型侧：逐骨骼参数、多纹理、半透明排序，全都要走「自定义 pipeline + UBO + 可入队 DrawCommand」。所以主线改为 WP1 → WP2，WP3 与 WP1 并行推进，谁先完成都不阻塞对方。
2. **把粒子拆成 4a/4b，把「等外部 jar」的部分整体推到 M5。** 旧清单把 AAA 放在 P1，但 `gradle.properties` 已经写明没有 1.21.11 版本线——按 P1 排会一直阻塞。拆开后 WP4a 可以立刻做，AAA 部分明确标为「外部阻塞」而不是「欠账」。

## 5. 架构决策记录

| # | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| **ADR-1** | 模型着色走「自定义 `RenderPipeline` + std140 UBO + 手写 `RenderPass`」，不复用 `RenderLayer` | `RenderLayer` 只绑引擎内建 uniform，tint/whiten/glint 是逐 draw 变化的片元参数，无法随层传递（§2.4 `ScreenQuadPass` javadoc 原文佐证） | 多约 400–600 行地基代码；要自己管顶点缓冲上传（但几何本来就每次重发，成本为零） |
| **ADR-2** | 自定义绘制包装成 `FormTranslucentQueue.DrawCommand` 入队，**不绕开队列** | 保住半透明远近排序、`StencilMap` 拆分、Iris 世界表单的特殊分支（`isActive()` 里判 `isIrisShadowPass`/`isIrisWorldForms`） | 依赖 `DrawCommand.draw()` 在 flush 期能开 pass（spike S1） |
| **ADR-3** | 逐骨骼参数 v1 走「逐 draw UBO 多次提交」，v2 才走 UV1 swatch 查表 | v1 改动最小（`ModelInstance` 本来就逐 group 循环），v2 才能做到「一次 draw 搞定整个模型」；但 v2 要复用被上游占用的 overlay 通道，风险高 | v1 的 draw 次数与骨骼数线性相关，复杂模型（20+ 骨骼）可能掉帧；v2 需要改 `FormOverlay` 语义 |
| **ADR-4** | 版本分源：同名双实现放 `java-1.20.x` / `java-1.21.11`，互斥挂载；共享层只放数据与反射 | `sourceSets.excludes` 会按相对路径同时排掉两个目录的同名文件（`build.gradle:378-381` 已踩过） | 共享层不能出现对任一版本类的编译期引用 |
| **ADR-5** | 平台差异一律运行期 `Class.forName` 探测，不引入编译期版本常量 | 沿用 `BBSPlusPlusModClient.hasClass`（line 75）的既有约定，注释已明确「不再维护 12111 副本」 | 探测失败是静默的 → 必须配 WP0 的一次性日志 |
| **ADR-6** | 不再使用任何 GL 立即状态（`RenderSystem.enableBlend` 等），一律走 pipeline/batcher 声明 | 1.21.11 已移除这些全局调用 | 每个效果都要显式声明 blend/depth，代码更啰嗦 |
| **ADR-7** | 屏幕后处理（WP3）走**原生** `PostEffectPipeline` + `PostEffectProcessor`，不手写多 pass 链；手写 `ScreenQuadPass` 只作为退路 | 上游 `InterfaceBlur` 已在 1.21.11 上用它跑通 5 级 ping-pong（`parseEffect` 支持纯代码构造 pipeline，无需 JSON）；pass 自带状态恢复，天然多 pass，省掉 WP3 对 WP1 的依赖 | 每个效果要写成独立 `.fsh` + std140 uniform block，691 行 `ColorGradeRenderer` 的 GL 调用无法复用，只能搬数学 |
| **ADR-8** | 1.21.11 专属 mixin 一律 `require = 0`（`injectors.defaultRequire: 0`），命中与否由启动自检 `GradeSelfCheck` 打日志 | 这四份注入全是纯客户端表现层（调色/光效/UV/预览）；`require = 1` 一旦选择器对不上就**启动即崩**，代价远大于功能不生效。而 `require = 0` 的静默失败可以用「反射看 handler 是否被合并进目标类」来补偿，不需要进世界 | 必须维护自检的 handler 名单（新增注入时要同步加一条），否则自检会漏报；失败时游戏正常但功能静默（日志 `WARN` 点名） |
