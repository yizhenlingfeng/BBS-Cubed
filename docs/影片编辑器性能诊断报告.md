# BBS 影片编辑器掉帧诊断报告

> 目标客户端：`E:\mc\.minecraft\versions\起源领域`（BBS 2.7 + 18 个 BBS 系附属 + 100 余个其它模组）
> 分析对象：打开「影片编辑器」（UIDashboard → UIFilmPanel → UIFilmPreview）后的每帧开销
> 方法：客户端 jar 全量反编译（Vineflower 1.10.1）→ 逐模组静态审计每帧注入点 → 结合客户端实际配置（`config/bbs/settings/bbs.json`）估算
> 说明：**占比为静态分析的相对估算区间，不是 GPU/CPU 计时器实测值**；第 7 节给出 15 分钟可完成的实测标定流程。

## 一、结论速览

| # | 嫌疑来源 | 每帧在干什么 | 触发条件 | 估算占帧时间 | 证据强度 |
|---|---------|-------------|---------|-------------|---------|
| 1 | **VFX-LIGHTS** (`vfxlights`) | 每盏带阴影的灯：6 面 × 1024² 阴影 tile 逐块 clear 并把**全部影片 actor / 实体 / 方块模型重画一遍**；再额外 3 个 mask pass 把 actor 再各画一遍 | 装了就在世界渲染事件里跑；有灯/阴影时放大 | **15–30%**（有 2 盏投影灯时） | 强（源码 + 多次循环） |
| 2 | **BBS 本体：影片 actor 渲染 + 轨道求值** | 每帧对每个 replay 求值全部属性轨道、pose、装备；再在 1280×720 的影片 FBO 里渲染所有 actor | 打开编辑器且影片里有 replay | **12–22%** | 强 |
| 3 | **RefreshedUI** (`refreshedui`) | 把 BBS 的每个圆角矩形/按钮/列表行/clip 背景从「批处理」改成**每次一个独立 drawcall**（BufferBuilder + 立即 draw） | 只要 UI 里有圆角元素（编辑器满是） | **8–15%** | 强（`Batcher2DMixin:301-315`） |
| 4 | **BBS：InterfaceBlur 界面模糊** | 8 个全屏 pass（4 级下采样 + 4 级上采样）@ 2560×1440 | `interface_blur=true`（当前 **开**）+ 有背景图 `bg2.png` | **8–12%** | 强（`InterfaceBlur.java:62-82`） |
| 5 | **BBS 本体：UI 时间轴 / 预览面板重绘** | 每帧重画 clips、轨道、关键帧、标尺、波形 | 打开编辑器 | **6–12%** | 中 |
| 6 | **BBS-VFX** (`bbsvfx`) | OIT 双 MRT FBO 全屏清 + 每束光/烟/穹顶/裂纹/标签各一次**全屏颜色 blit + 全屏 quad** | 影片里用了对应 VFX | **5–12%**（条件） | 强 |
| 7 | **BBS-POV** (`bbspov`) | 3–4 次全分辨率深度 blit；手部模式再全屏 clear + 重渲整只手 + `glReadPixels` 同步回读 | POV/手部/深度相关功能 | **3–8%**（条件） | 强 |
| 8 | **IRLite** (`irlite`) | 每帧扫全世界实体 + 方块实体 + 全部 replay，逐 Form 树发灯；每 caster 再重渲一遍进阴影图 | IRLite 光照启用 | **2–6%** | 强 |
| 9 | **BBS-Cubed** (`bbsplusplus`) | 着色器曲线 1×1 FBO + `glFinish`；调色全屏拷贝+pass；纹理补间整张上传；运动轨迹签名序列化 | 对应功能开启时 | **4–8%**（分散） | 强（`ShaderCurveState.java:75` 等） |
| 10 | **镜像/多窗口** | 镜像：整场景第二遍渲染；分离窗口：每帧把整套菜单渲进 FBO + 切上下文 | 面板打开时 | **5–15%**（条件） | 强 |

> 排序逻辑：**当前配置下必然发生**的（2/3/4/5）与**只要影片里有灯就必然发生**的（1）优先解决。

## 二、编辑器每帧渲染管线（打开影片编辑器后）

| 步 | 发生了什么 | 位置 | 量级 |
|----|-----------|------|------|
| 1 | 主 framebuffer 被换成影片尺寸的 custom FBO：当前 `preview_size_mode=1` → **1280×720** | `UIFilmPanel.java:643 applyPreviewSizeToBBS()` | 3.7 Mpx→0.92 Mpx（比 2560×1440 省 4×） |
| 2 | 世界/实体/影片 actor 渲染（地形、方块、模型、IK、POSE） | `BaseFilmController.java:308 render()` → `:361 renderEntity` | 随 replay 数 × 骨骼数 |
| 3 | 每个 replay 的属性轨道求值 + 装备变换 + item use 计算 | `BaseFilmController.java:232 startRenderFrame()` | 随轨道数 × 关键帧 |
| 4 | 每部 film controller 渲染 | `Films.java:258 render(context)` | 随 controller 数 |
| 5 | 世界渲染结束：附加 pass 链 | `BBSRendering.onWorldRenderEnd` | 见下 |
| 6 | VFX-LIGHTS 体积光/阴影/合成 | `vfxlights/mixin/client/BBSRenderingMixin`（HEAD 无条件） | 灯数 × tile |
| 7 | BBS-VFX OIT 与各体积 pass | `bbsvfx/BBSRenderingImpactMixin:35-58` | VFX 数量 |
| 8 | 调色 pass（两份实现：bbsplusplus / bbslezy） | `ColorGradeRenderer`（两者同名类） | 有调色 clip 时 |
| 9 | 影片 FBO → 屏幕 `glBlitFramebuffer(1280×720 → 2560×1440)` | `BBSRendering.java:316 onRenderBeforeScreen()` | 3.7 Mpx/frame |
| 10 | Dashboard 背景 + InterfaceBlur 8 pass | `UIDashboard.java:291-296` → `InterfaceBlur` | 3.7 Mpx × 8 |
| 11 | 编辑器 UI（时间轴、clip、轨道、关键帧、预览边框、按钮） | BBS UI + bbsplusplus + refreshedui | drawcall 数 × 元素数 |
| 12 | 条件：POV 深度/stencil、镜像、分离窗口、IRLite 扫描 | 见第三节 | 条件 |

关键洞察：**打开编辑器后世界其实是以 720p 渲染的（第 1 步），比正常 1440p 玩耍更省。** 因此掉帧的主因几乎不可能是地形填充率，而是：
1. 影片 actor 的 CPU 侧求值 + 多次重复渲染（第 2/3 步，被 vfxlights/IRLite 放大）；
2. 全屏 pass 叠加（第 6/8/10 步）；
3. UI drawcall 爆炸（第 11 步，被 refreshedui 放大）。

## 四、场景化帧预算（估算）

以 60 FPS = 16.7 ms 为基线，「打开编辑器」相对「正常游玩」的额外负担：

| 场景 | 组成 | 预计帧时间 | 预计 FPS |
|------|------|-----------|---------|
| S0 正常游玩（不进编辑器） | E1 + E2 + 少量 HUD | 8–12 ms | 80–120 |
| S1 打开编辑器、空影片 | A1–A6 + B1–B5 + 世界 720p | 12–18 ms | 55–80 |
| S2 编辑一部 5 replay 的影片（无灯无特效） | S1 + A1/A2 放大 + 影片 actor | 18–26 ms | 38–55 |
| S3 S2 + 2 盏投影灯（vfxlights 默认） | + C1–C4（actor 被重画 4–8 遍）+ 阴影 6 面×2 | 28–45 ms | 22–35 |
| S4 S3 + VFX 特效 + 调色 + 界面模糊 | + D1–D5 + A5 | 35–60 ms | 16–28 |

> 结论：**S2 → S3 的断崖（约 −35% FPS）几乎全部来自 vfxlights 的"每灯每帧重画所有 actor"**；这与「一打开编辑器就卡」的观感一致，因为编辑器一打开就会把影片里的 actor 全部拉起。
